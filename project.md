Техническое описание проекта: Платформа управления хакатонами

1. Общее описание

Менеджер хакатонов — это комплексное SaaS-решение, предназначенное для автоматизации процессов организации хакатонов. Система обеспечивает полный цикл: от создания лендинга и настройки форм регистрации до управления составами команд и экспорта финальных данных.

2. Ролевая модель

В системе предусмотрены три роли:

Администратор: Управляет сущностями вне конкретного хакатона. Создает учетные записи организаторов, создает хакатоны, назначает организаторов на хакатоны, управляет глобальными настройками и архивом мероприятий. Администратор не обязан быть организатором каждого хакатона, но может одновременно быть назначенным организатором одного или нескольких хакатонов.

Организатор: Управляет только теми хакатонами, на которые он назначен администратором. Внутри назначенного хакатона организатор управляет лендингом, метаданными, регламентом, динамическими формами, заявками, командами, модерацией участников и экспортом данных.

Участник (Игрок): Имеет личный кабинет для управления персональными данными и участия в командах.

Разграничение зон ответственности: всем, что находится снаружи конкретного хакатона, управляет администратор. Всем, что относится к содержимому и процессам внутри конкретного хакатона, управляют назначенные организаторы этого хакатона. Администратор может выполнять действия организатора только для тех хакатонов, где он назначен организатором, либо через отдельные административные операции назначения.

3. Функционал Администратора

3.1. Управление организаторами

Администратор создает учетные записи организаторов, просматривает список организаторов и при необходимости изменяет их данные или блокирует доступ.

3.2. Управление хакатонами снаружи

Администратор создает новые хакатоны, переводит их между глобальными состояниями, выбирает активный хакатон, просматривает архив и назначает организаторов на конкретные хакатоны.

3.3. Назначение организаторов

Один хакатон может иметь одного или нескольких организаторов. Один организатор может быть назначен на несколько хакатонов. Администратор также может назначить самого себя организатором хакатона.

4. Функционал Организатора

4.1. Управление назначенными хакатонами

Жизненный цикл внутри хакатона: настройка опубликованного содержимого, просмотр состояния регистрации и подготовка данных события. Создание хакатона и назначение организаторов остаются зоной администратора.

Редактирование: Изменение названия, дат проведения и других метаданных.

Регламент: Загрузка и обновление PDF-файла с официальными правилами.

4.2. Конструктор форм (Регистрация и Обратная связь)

Назначенный организатор может гибко настраивать поля форм внутри своего хакатона. Поддерживаемые типы полей:

Текстовое поле (с валидацией длины, однострочное или многострочное).

Контактные данные (Телефон, E-mail, Ссылки).

Дата, Дата и Время, Время.

Выбор (Чекбокс, Радиокнопка).

Загрузка файлов.

Управление видимостью: Скрытие или добавление полей для конкретных этапов или категорий участников.

4.3. Модерация и Управление командами

Таблица заявок: Просмотр всех команд, времени подачи и составов.

Статусы: Присвоение статуса «Допущен к участию».

Редактирование составов: Принудительное изменение участников в командах.

Санкции: Дисквалификация отдельных участников или команд целиком.

Экспорт: Выгрузка данных в форматах Excel или CSV.

5. Функционал Участника

5.1. Профиль пользователя

Каждый пользователь имеет личный кабинет со следующими обязательными и опциональными полями:

ФИО*.

Учебное заведение* и Курс*.

Фото и Аватар.

Дополнительные данные: Аллергии на еду, размер футболки, контакты (VK, TG).

Ограничения: Минимальное и максимальное количество участников в команде настраивается назначенным организатором внутри хакатона. Поля добавляются и удаляются динамически назначенным организатором, постоянны только ФИО и аватар. Если организатор скрывает поле, оно не показывается в формах, но исторические значения сохраняются.

5.2. Капитанские полномочия

Каждый участник может пометить себя (или быть помеченным) как капитан. В одной команде может быть только один капитан.

Редактирование названия команды.

Управление составом (добавление/удаление участников).

Удаление команды или снятие её с соревнования.

6. Процесс регистрации и логика команд

6.1. Подача заявки (Flow)

Инициация: Капитан заполняет название команды и список участников (от 1 до 5).

Идентификация участников:

Если участник уже есть в системе — указывается его логин.

Если участника нет — заполняются его данные в расширенной форме (поля регулируются админкой, это некоторое подмножество полей пользователя: например, ФИО, учебное заведение и курс).

Завершение: Система создает команду и привязывает к ней участников.

Связи: Участник может состоять только в одной команде в рамках одного хакатона. История участия в разных командах на прошлых хакатонах сохраняется в профиле.

6.2. Адаптация новых участников (Onboarding)

Если капитан зарегистрировал новых пользователей «с нуля», он получает индивидуальные ссылки-приглашения для каждого. Перейдя по ссылке, новый участник выбирает сценарий:

«Я уже участвовал ранее»: Вход по существующему логину/паролю (связывание аккаунтов).

«Я новичок»: Создание логина и пароля и завершение регистрации профиля. Если
конкретно, то пользователь для завершения регистрации должен заполнить
обязательные поля. Необязательные поля заполнять тоже можно, но не обязательо.
Те поля, которые капитан уже заполнил, пользователь увидит заполненными, но
сможет изменять значения.

7. Технические особенности

Генерация логинов: Автоматическое создание уникальных идентификаторов на основе ФИО.

Архитектура данных: Хранение истории переходов игрока между командами от хакатона к хакатону.

Безопасность: Разграничение прав доступа между капитанами и обычными членами команды.

8. Текущее состояние реализации frontend

Актуальная ветка содержит рабочий frontend-каркас платформы хакатонов и mock backend.

8.1. Готово

Визуальный стиль: приложение переведено на Frutiger Aero направление: стеклянные MUI-панели, голубой/зеленый/белый градиентный фон, полупрозрачные контролы, водно-небесная атмосфера и иконки в ключевых действиях.

Mock backend: реализован `mock-backend/server.mjs` с auth, пользователями, организаторами, хакатонами, form fields, командами, статусами, приглашениями и частью legacy quote endpoints для обратной совместимости.

Хакатоны: есть список хакатонов, карточка хакатона, получение активного хакатона, получение полей регистрации.

Администрирование: есть форма создания организатора, форма создания хакатона, выбор организатора при создании, отдельное назначение организатора на существующий хакатон, списки организаторов и хакатонов.

Командная заявка: участник может создать команду, добавить существующих участников по логину, добавить новых участников с ФИО/почтой/учебным заведением/курсом, выбрать капитана и получить invite-ссылки для новых участников после создания заявки.

Таблица заявок: организатор или назначенный администратор видит команды в таблице, фильтрует их по статусу, видит капитана, состав, дату подачи и moderation reason.

Модерация команд: из UI доступны допуск, отклонение, дисквалификация команды и дисквалификация отдельного участника.

Экспорт заявок: текущую таблицу заявок можно выгрузить в CSV или XLSX из UI.

Redux/API: подключены слайсы `auth`, `settings`, `hackathons`, `teams`, `admin`; legacy `quotes` еще остается. API-адаптеры лежат в `frontend/src/api/hackathonApi.ts`.

Доменные helpers: `frontend/src/domain/access.ts`, `adminForms.ts`, `teamForms.ts`, `teamModeration.ts`, `teamExport.ts` покрывают правила доступа, валидацию, преобразование form values в payload, отображение модерационных данных и экспорт заявок.

Тесты: `tests/access.test.ts` покрывает правила доступа, формы админки и формы командной заявки. Перед документированием проходили `npm run lint`, `npm test`, `npm run build`.

8.2. Частично готово

Список/архив хакатонов: общий список есть, но отдельного UI-фильтра архива и административного архивного представления пока нет.

Переключение активного хакатона: endpoint в mock backend есть, но frontend API helper, thunk и UI еще не доделаны.

Динамические поля: типы и получение form fields есть, но конструктора динамических полей в UI пока нет.

8.3. Не готово

Загрузка PDF-регламента из UI.

Конструктор динамических полей.

Invite onboarding: отдельная страница перехода по invite-ссылке, привязка существующего аккаунта или завершение регистрации нового участника.

API adapter tests и компонентные тесты ключевых форм.

Удаление legacy quote-кода: `QuoteCard`, `Quotes`, `RandomQuote`, `CreateQuote`, `store/quote`, `store/user`, старые `entities/quote` и `entities/user`.

8.4. Рекомендуемый следующий блок

Следующим лучше брать админское управление хакатонами:

1. добавить список/архив хакатонов с фильтрами;

2. добавить переключение активного хакатона;

3. добавить загрузку PDF-регламента;

4. после этого перейти к конструктору динамических полей.

Практически лучше сначала закрыть список/архив и переключение активного хакатона: mock endpoint активации уже есть, а UI админки сейчас показывает хакатоны без управления жизненным циклом.
